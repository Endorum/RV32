# rv32 als zwei RAD-C++-Projekte — Design

**Datum:** 2026-10-26
**Status:** Entwurf, wartet auf Review
**Teil 1 von 2.** Teil 2 ist ein "offener Projektmodus" in RAD C++ (eigenes Repo, eigener Spec), siehe Abschnitt 8.

## 1. Ziel

Das Repo besteht danach aus genau zwei Projekten, die beide in RAD C++ geöffnet werden:

- **`emulator/`**: der Qt-Emulator (heute `rv32emu-qt/`), RAD-C++-Projekt `rv32emu`, Typ `qt-widgets`.
- **`software/`**: Firmware und Kernel als **ein** Cross-CMake-Build, RAD-C++-Projekt `software` mit selbst
  geschriebener `CMakeLists.txt`.

Gemeinsam ist nur `platform/` (Hardware-Vertrag), das außerhalb beider Projekte bleibt.

Erfolg heißt: Man öffnet `software/software.radcpp` in RAD C++, drückt Play, die Software wird gebaut, und der
Qt-Emulator startet mit `rom.bin` und `disk.img`. VS Code wird für nichts mehr gebraucht. Das Repo ist so
klein und übersichtlich wie möglich.

**Nicht in diesem Design:** Änderungen an RAD C++, RISC-V-Debugging aus der IDE (GDB-Stub), neue Funktionen
in Emulator oder Software außer `-headless`.

## 3. Header und Units

Header bleiben neben ihren Quellen (`src/kernel/mm/page.c` + `page.h`); `software/include/` gibt es nicht.
`rv32_image()` gibt jedem Image nur die Include-Pfade seiner Module und Bibliotheken; so sieht die Firmware nie
Kernel-Header. RAD C++ bildet Units aus Ordner + Basisname relativ zu `src/` oder `include/`, unabhängig davon,
in welchem der beiden Ordner der Header liegt (`UnitRegistry::build`). `kernel/mm/page` ist also eine Unit mit
`.c` und `.h`. `.S`-Dateien sind gewöhnliche Dateien im Baum.

Der Emulator bleibt bei der RAD-C++-Konvention `src/` + `include/`.

## 4. Software-Build

### 4.1 `software/CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.20)
set(CMAKE_TOOLCHAIN_FILE "${CMAKE_CURRENT_LIST_DIR}/cmake/riscv-toolchain.cmake"
    CACHE FILEPATH "RISC-V cross toolchain")
project(rv32_software LANGUAGES C ASM)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
include(cmake/rv32-image.cmake)

add_subdirectory(src/firmware firmware)
add_subdirectory(src/kernel   kernel)

# + Startskript build/software (4.3)
```

RAD C++ erkennt die Datei als fremd (kein Kopf "Generated by RAD C++"), lässt sie unangetastet und baut sie
trotzdem (`RunController::beginPipeline`). Die Configure-Argumente der IDE (`-G Ninja`,
`-DCMAKE_BUILD_TYPE=Debug`, `-DCMAKE_PREFIX_PATH=…`) stören den Cross-Build nicht.

### 4.2 Unter-CMakeLists und `rv32-image.cmake`

- `src/firmware/CMakeLists.txt` und `src/kernel/CMakeLists.txt` verlieren `cmake_minimum_required`, die
  Toolchain-Zeile, `project()` und das `include` von `rv32-image.cmake`. `rv32_image(...)`-Aufrufe,
  Modullisten und das Packen von `disk.img` bleiben gleich. Das `run`-Ziel der Firmware entfällt (ersetzt durch
  4.3). Die Kopfkommentare werden auf die neuen Pfade und den Build über `software/` umgeschrieben.
- `rv32-image.cmake`, Pfade:

  | Variable | neu |
  |---|---|
  | `RV32_ROOT` | `software/` (Ordner über `cmake/`) |
  | `RV32_PLATFORM` | `${RV32_ROOT}/../platform` |
  | `RV32_SW_COMMON` | `${RV32_ROOT}/src/common` |
  | `RV32_BUILD_ROOT` | `${RV32_ROOT}/build` |
  | `RV32_DISK_IMAGE` | `${RV32_BUILD_ROOT}/disk.img` |
  | `RV32_MKIMAGE` | `${RV32_ROOT}/tools/mkimage/mkimage.sh` |
  | `RV32_EMULATOR` | `${RV32_ROOT}/../emulator/build/rv32emu` |

  Der Rest der Datei (Flags, `rv32_image()`) bleibt unverändert.

Ausgaben, alle unter `software/build/`: `firmware/rom.{elf,bin,map,ld}`, `firmware/dis/`,
`kernel/kernel.{elf,bin,map,ld}`, `kernel/dis/`, `disk.img`, `compile_commands.json`.

### 4.3 Play: Startskript `build/software`

RAD C++ startet bei Run immer `build/<name>`. Die `CMakeLists.txt` erzeugt deshalb mit `file(GENERATE)` ein
ausführbares Shell-Skript `build/software`:

```sh
#!/bin/sh
EMU="<RV32_EMULATOR>"
[ -x "$EMU" ] || { echo "emulator not built: $EMU -- open emulator/rv32emu.radcpp in RAD C++ and build it" >&2; exit 1; }
exec "$EMU" -firmware="<build>/firmware/rom.bin" -harddisk="<build>/disk.img" "$@"
```

Ein Ziel `launcher ALL` hängt von `rom_bin` und `disk` ab, damit Play immer mit frischen Images startet.
`software.radcpp` hat `[run] args = []`; zusätzliche Emulator-Schalter (z. B. `-headless`, `-d`) werden dort
eingetragen und vom Skript durchgereicht.

### 4.4 `CMakePresets.json`

Ein Configure-Preset `default` (Ninja, `binaryDir = ${sourceDir}/build`) und Build-Presets `default` und `run`.
`run` baut das Ziel `run` (`add_custom_target(run COMMAND build/software USES_TERMINAL)`, hängt von `launcher` ab). Damit geht im Terminal:
`cmake --preset default && cmake --build --preset default`.

## 5. Emulator

- `rv32emu-qt/` wird mit `git mv` zu `emulator/`.
- `rv32emu-qt.radcpp` → `rv32emu.radcpp`, `name = "rv32emu"`. `CMakeLists.txt` wird dazu passend neu erzeugt
  (gleicher Inhalt wie heute, nur der Name); das Binary heißt wieder `emulator/build/rv32emu`.
- `project.cmake` bleibt inhaltlich gleich (Kommentar ohne Verweis auf den alten `emulator/`).
- `.radcpp`-Run-Argumente: `-firmware=../software/build/firmware/rom.bin`, `-harddisk=../software/build/disk.img`.

### 5.1 `-headless`

Neuer Schalter in `Config`/`parse_arguments` und in `showUsage`. Mit `-headless` erzeugt `main.cpp` kein
Fenster und läuft wie der frühere Konsolen-Emulator:

```cpp
Machine machine(config);
machine.start();
while (!machine.halted()) {
    machine.step();
    std::cout << machine.uart_output() << std::flush;   // UART puffert seit dem Qt-Umbau
}
```

Eingabe kommt wie bisher über `UART::tick()` von stdin (Raw-Modus aus `init_terminal`). Ohne `-headless`
bleibt alles wie heute. Mit `-headless` wird kein `QApplication` erzeugt (kein Fenster, kein Dock-Symbol);
`parse_arguments` bekommt in beiden Fällen dieselben Argumente.

## 6. Root-Dateien

- `README.md`: neu, kurz. Was die zwei Projekte sind, wer was sieht (Tabelle Include-Pfade: emulator →
  platform; firmware → platform, common, firmware; kernel → platform, common, kernel), wie man beide in
  RAD C++ öffnet, Terminal-Build für `software/`, Hinweis auf `-headless`.
- `.gitignore`: `build/` (greift in beiden Projekten), `.DS_Store`, `.cache/`, `*.radcpp.user`.

## 7. Ablauf und Prüfung

Eigener Branch (Worktree nach Superpowers-Skill). Jeder Schritt ist ein Commit.

0. **Ausgangsmessung:** Firmware und Kernel mit den heutigen Presets bauen, `shasum` von `rom.bin`,
   `kernel.bin`, `disk.img` im Scratchpad festhalten.
1. **Emulator:** `rv32emu-qt/` unverändert committen; alten `emulator/` und `tests/` löschen; `git mv` nach
   `emulator/`, umbenennen; `-headless` einbauen.
   *Prüfung:* Configure und Build mit genau den Argumenten aus `Toolchain::configureArgs`
   (inkl. RAD-C++-SDK im Prefix-Pfad); `emulator/build/rv32emu -headless -firmware=<alte rom.bin> -harddisk=<alte disk.img>`
   zeigt die Firmware-Ausgabe auf der Konsole.
2. **Software:** `git mv` von `sw/common`, `sw/firmware`, `sw/kernel`, `cmake/`, `tools/` nach `software/`;
   neue Haupt-`CMakeLists.txt`, Presets, `software.radcpp`, Startskript; Unter-`CMakeLists` und
   `rv32-image.cmake` anpassen.
   *Prüfung:* `software/build` frisch konfigurieren (gleiche Argumente wie RAD C++) und bauen; `rom.bin`,
   `kernel.bin` und `disk.img` sind **byteweise gleich** zur Ausgangsmessung (der Code nutzt kein `__FILE__`);
   `compile_commands.json` existiert; `build/software -headless` bootet bis zur Firmware-Shell und lädt den Kernel.
3. **Aufräumen:** Root-`CMakeLists.txt`/`CMakePresets.json`, `.vscode/`, Reste löschen; README, `.gitignore`.
   *Prüfung:* `git grep` findet keine alten Pfade mehr (`sw/`, `rv32emu-qt`, `tests/isa`, `build/firmware` außer
   unter `software/build`, `build/all`); `git status` sauber.
4. **Abnahme durch Alex in RAD C++:** beide Projekte öffnen; Play im Emulator; Play in `software` startet den
   Qt-Emulator, Firmware-Shell erscheint, Kernel bootet; Units im Baum (`kernel/mm/page` mit `.c` und `.h`).

## 8. Eingaben für Teil 2 (offener Projektmodus in RAD C++)

Gesammelt aus diesem Umbau, nicht hier umzusetzen:

- Eigene `CMakeLists.txt` als gewollter Modus (`type = "cmake"`), ohne den Hinweis "fremd" bei jedem Build.
- Frei wählbarer Run-Befehl in der `.radcpp` (Programm + Argumente) statt `build/<name>`; danach entfällt das
  Startskript.
- Optional Toolchain-Datei bzw. Configure-Preset in der `.radcpp`.
- Kein Zwang zu `src/`; Find in Files über den ganzen Projektordner.
- "New Unit" mit Option "Header neben die Quelle".
- `.S` als Quelle einer Unit (z. B. `trap.S` zu `tf.h`).
- clangd mit `--query-driver` für Cross-Compiler, damit die Systemheader des RISC-V-GCC gefunden werden.

## 9. Risiken

- **clangd und der RISC-V-GCC:** Ohne `--query-driver` kann clangd einzelne Flags oder Header des Cross-
  Compilers nicht auflösen und zeigt falsche Fehler im Editor an. Der Build ist davon nicht betroffen; Lösung
  in Teil 2.
- **Byteweiser Vergleich schlägt fehl:** Dann zuerst die Ursache finden (z. B. andere Reihenfolge der
  Quellen durch neue Pfade), nicht die Prüfung lockern. Eine geänderte Link-Reihenfolge ist nur akzeptabel,
  wenn die `.map`-Dateien das als einzigen Unterschied zeigen und die Software unverändert bootet.
